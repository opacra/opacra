# Code review, October 2026

Before the public testnet, Opacra's changes to Monero v0.18.5.1 (about 600 lines in
57 files, `git diff 4f92268..f4d6fac`) were reviewed by four independent AI reviewers
that had not seen the code being written, plus a fifth review of the fixes. Each area
was checked by reading the code and by running the real consensus code in test
harnesses. This is not a substitute for a paid human audit before mainnet.

## Result

The coin's own maths is sound. Rewards, the 10M curve, the tail, the slow start, the
genesis block, the fork table and the LWMA difficulty all match the spec exactly, and
the C++ agrees with the Python model to the atomic unit (1.66 million simulated blocks,
20-year emission schedule). Network isolation from Monero was confirmed with live nodes.

The bugs were in how nodes accept blocks, plus launch-kit and documentation problems.
All are fixed in this release.

| Severity | Finding | Fix |
|---|---|---|
| High | A side chain forked from far back could claim hours of "slow" timestamps and lower its difficulty to 1, then flood nodes with free blocks (no checkpoints yet). | Side-chain blocks must have at least 1/4 of the main chain's difficulty once the chain is past its first hour (`alt_difficulty_acceptable`). No reorg-depth limit. |
| Medium | In the first 11 blocks the main chain and side chains applied different median-time-past rules, so nodes could get stuck on different chains at launch. | One rule for both: the 11 previous blocks including genesis, no check below height 11. |
| Medium | With a 3-minute future time limit, a node whose clock was a few minutes slow treated honest blocks as invalid and banned the peers relaying them. | A block with valid proof of work that is only ahead of our clock is rejected for now without penalising the peer, as in Bitcoin. |
| Medium | Monero's block-size constants (300 kB penalty-free zone, 100,000-block long-term window) were kept unchanged, which at 30 s blocks allows 4 times the chain growth per day. | Scaled to match Monero per unit of time (see the decision below). |
| Low | Side-chain blocks were not held to the future time limit. | Checked after proof of work. |
| Low | Side-chain coin totals included fees, so templates built on a side chain had the wrong reward. | Count only newly created coins; miner notification after a reorg uses the stored total. |
| Low | The generated-coins total stopped at 10M in year 19.4 although the tail continues. | Keeps counting (consensus unchanged); miners still see it clamped to 10M. |
| Low | The weekly difficulty recheck rescanned from genesis, holding the chain lock longer every week. | Rechecks the last 20,160 blocks. |
| Low | Genesis output used a random key whose secret was discarded. | Mainnet genesis will use a key derived from the genesis message that no one can hold. |
| Low | Wallets ignored outputs above 10M; OpenAlias looked for `oa1:tca`; wrong port in wallet help; mining estimate used 356 days. | Fixed. |
| Low | Testnet/stagenet ports (39960+, 49960+) were inside Linux's ephemeral port range. | Moved to 29970-29972 and 29980-29982. |
| Low | No testnet seed-node recipe; the seed script would switch on a firewall and could cut off other services on a shared server. | `seed-node-setup.sh <package> testnet`; only adds a rule when ufw is already active. |
| Low | Docs referred to tooling that does not exist (`contrib/guix`), old `Ta` prefixes, wrong package names; Monero's root Dockerfile was still present. | Corrected; root Dockerfile removed, `.dockerignore` added. |

The fix review found that a first version of the side-chain fix (a 720-block reorg-depth
limit) opened a free-spam path and could split nodes after an eclipse attack; it was
replaced by the difficulty floor above before release.

## Tests

- `tests/opacra`: 107 checks, 0 failures (adds the difficulty floor, the scaled block-size rules, a simulated
  side-chain attack and the uncapped coin total). Under the attack, at most 18 side
  blocks get through, none cheaper than 1/4 of a main-chain block.
- `contrib/testnet/block_rules_test.py` (new): 12/12 on this build. The previous build
  fails the side-chain future-time, median-time and slow-clock checks, reproducing the bugs.
- `contrib/testnet/functional_test.py`: see `docs/TEST_REPORT.md`.
- Launch-week simulation with the real daemon code (40,000 blocks, five scenarios):
  mean block time 29.9–31.9 s in every scenario; after a 90% hash-rate drop the first
  60 blocks average ~106 s and difficulty recovers in ~110–165 blocks; timestamp
  manipulation only raises difficulty a few percent and earns the attacker nothing.

## Decision: block size at 30-second blocks

Monero's 300 kB penalty-free block size and its 100-block and 100,000-block median
windows were designed for 2-minute blocks; copied unchanged they would have allowed 4
times more chain growth per day at 30 s, with spam 4 times cheaper relative to the block
reward. Decided 3 October 2026: scale them so Opacra matches Monero per unit of time.
75 kB zone (about 40 typical transactions per block before blocks grow with demand),
400-block short-term median (3.3 hours) and 400,000-block long-term median (139 days).
The default wallet fee is 1,300,000 atomic units per byte while blocks are not full, about
0.0028 OPCA for a typical 2-input transaction (median of 470 testnet payments, 4 Oct 2026). Monero's fee
formula divides by the square of the penalty-free zone, so the smaller zone makes fees 16 times higher
relative to the block reward, or 4 times Monero's relative to coins created per hour. (An earlier
version of this report gave ~0.00025 OPCA; that figure was wrong by a factor of ten.) The largest single
transaction is about 36.9 kB (around 50 inputs; wallets split larger spends). Changing
this after mainnet would need a hard fork; before launch it costs one rebuild.

## Development fund (added 3 October 2026)

Decided: 5% of every block's subsidy to a development fund, from block 1 with no end date
(fees go entirely to miners). The design went through three rounds of independent review
before release:

| Round | Design | Problem found | Outcome |
|---|---|---|---|
| 1 | Per-height key in the coinbase's "additional public keys" field | Miners could put junk in the miners' slots of that field and make fund outputs unspendable with the stock wallet; pools' `reserved_offset` moved into that field | Replaced |
| 2 | Fund output keyed from the coinbase's random key, checked with the published view key | A miner could reuse an earlier block's key (or a small-order point) so two fund outputs share one key, and only one can ever be spent | Replaced |
| 3 | Per-height key R_f appended as a second transaction public key, after the extra nonce | A junk extra public key could jam the fund wallet's key-image export and multisig signing | Fixed: the coinbase's public keys must be exactly [miner's key, R_f], both valid points; the wallet also uses the key recorded while scanning and skips malformed keys |

Also found and handled: XMRig 6.26 rejects coinbases with two outputs in solo (`--daemon`)
mode (a small patch is in `contrib/xmrig/`; pool mining is unaffected), and pool software
must credit miners from `expected_reward`, not the block header's reward, which includes the
fund (documented in `docs/MINING.md`).

Tests: `tests/opacra` 157/157 (fund share, keys, coinbase layout, wallet scanning maths);
`block_rules_test.py` 25/25, including blocks that short the fund by one atomic unit, change
its key, view tag or per-height key, empty it, or add a junk public key (all refused), and
pools writing 8- or 60-byte extra nonces (accepted); `functional_test.py` replays every
block's fund payment and checks that a view-only wallet built from the public view key sees
exactly what the chain owes the fund.
